# M3 Phase 2, Slice 1: security review (Gitleaks integration)

- **Date:** 2026-10-10
- **Scope:** the Gitleaks integration of [ADR-0010](../adr/0010-scanner-adapters-repository-snapshots-and-findings.md):
  - repository snapshots and the stdin channel;
  - the sandbox script;
  - the adapter, the findings contract, evidence and logging;
  - the Java planning gate.
- **Method:** adversarial review with the pinned Gitleaks 8.30.1 image. Every suspected
  behavior was verified empirically in a real sandbox before a fix was designed, and
  every fix has a regression test. Only synthetic credentials were used, generated at
  test time.
- **Threat model:** [Gitleaks scanner](../threat-model/gitleaks-scanner.md) (G1–G14)
- **Code:** uncommitted changes on top of `8ca4fe2`

## Confirmed defects

| ID | Severity | Area | Defect | Fix | Regression tests |
|---|---|---|---|---|---|
| D1 | **High** | Suppression | The upstream default ruleset (used through `[extend] useDefault = true`) contains **path-based allowlists** that a repository author controls by naming files: the global list skips `*.png`, `*.exe`, `*.pdf`, `go.sum`, lockfiles, `node_modules/`, `vendor/…` and any path containing `gitleaks.toml` (unanchored), and three rule-level lists skip, for example, `@octokit/auth-token/README.md` for GitHub tokens. Verified: real-format tokens in `creds.png`, `gitleaks.toml/hidden.py`, `node_modules/x/config.js` and `my.gitleaks.toml.py` were **not reported**. An extending config cannot clear the global list (Gitleaks rejects an empty allowlist) | The worker now supplies a complete ruleset, `scanners/gitleaks-rules.toml`: the upstream v8.30.1 default (SHA-256 `e163e53b…a329caf`) with every path-based allowlist removed, generated by `scripts/dev/derive-gitleaks-rules.py`, which refuses any other upstream file and verifies the result rule by rule. Value-based allowlists are unchanged | `test_file_names_cannot_hide_secrets_from_the_ruleset` (real container, 12 hiding places), `test_the_ruleset_has_no_path_allowlists_and_keeps_every_upstream_rule`, E2E (`assets/logo.png`) |
| D2 | **Medium** | Privacy | File paths were persisted verbatim in `findings.json` and hashed raw into fingerprints, so a credential committed as a file or directory name would be stored | Paths are persisted only in a **safe form**. Gitleaks also scans a worker-generated path manifest with the same rules; such detections become `FILE_PATH` findings and their components are replaced by `[redacted-N]` labels, with a heuristic for credential prefixes and high-entropy runs as defense in depth. Fingerprints use the safe path. Contract fields added: `location.target`, `location.path_redacted`, `input.paths_redacted` | `test_a_secret_in_a_file_name_becomes_a_redacted_path_finding`, `test_fingerprints_use_only_the_safe_path`, `test_secrets_in_file_and_directory_names_are_detected_and_redacted` (real), `test_secrets_in_file_names_are_never_stored` (integration: evidence, results, audit), E2E, 8 more unit tests |
| D3 | Low | Input integrity | The sandbox verified the extracted file **count** and types, but not names or content: a partial or altered extraction with the right count would have been scanned. BusyBox would extract links, FIFOs and duplicate entries before the checks ran (a symlink entry followed by `link/file` writes outside the input directory). An empty snapshot was reported as complete coverage | The script stages the archive and **lists it before extracting**: only plain files and directories; hard links (listed by BusyBox as files with `-> target`) refused; relative, unique names under `repo/`, `config/`, `meta/` only (new exit 75). After extraction, a `sha256sum` digest over every name and content must equal the worker's `extraction_sha256` (exit 72). Snapshot invariants are checked on construction; the archive builder refuses duplicate or conflicting entries. Empty input carries `EMPTY_INPUT` | `test_hostile_archive_members_are_refused_before_extraction` (10 real cases), `test_truncated_or_tampered_input_never_yields_a_scan`, `test_long_deep_and_unusual_names_extract_exactly`, `test_snapshots_refuse_unsafe_or_ambiguous_paths` (11 cases), `test_archives_cannot_overwrite_or_escape`, `test_the_extraction_digest_is_what_sha256sum_reports`, `test_an_empty_repository_is_flagged_not_clean` |
| D4 | Low | Error handling | Parser errors were raised inside `except` blocks, so each `ScannerError.__context__` held the original exception. A `JSONDecodeError` keeps the whole document, which can contain report text. Nothing logged it, but one `exc_info=True` would have leaked it | Parsing returns a sentinel and errors are raised outside `except` blocks; no `ScannerError` has a context or cause | `test_scanner_errors_carry_no_content_and_no_exception_chain` (4 cases) |

No Critical defects were found. No existing guarantee (no host mounts, sandbox controls,
lease fencing, tenant-scoped evidence, `INCOMPLETE` until M4) was weakened.

## Reviewed without defects (and tests added)

| Area | Result |
|---|---|
| Nested `.gitleaks.toml` / `.gitleaksignore` | Not loaded by Gitleaks (verified). `test_nested_suppression_files_are_inert` |
| Scanner environment | The sandbox gets no environment. The image's own `ENV` is only `PATH`, checked by a supply-chain guard (`test_the_image_sets_no_gitleaks_environment`). The isolation probe passes under the Gitleaks policy |
| CLI arguments | Constant script. Arguments are three worker-generated integers and a hex digest. No option that narrows reporting is passed (`test_the_command_is_constant_and_takes_only_worker_generated_values`) |
| Scanner output | Stdout is bounded and parsed strictly. Stderr is bounded and never logged or persisted (`test_scanner_stderr_is_never_logged`). Oversized reports fail with `RESOURCE_LIMIT_EXCEEDED`. Unexpected exit codes fail closed. Logs carry codes only (`test_logs_never_contain_file_names`) |
| Stdin writer | A sandbox or runtime CLI that exits without reading, or that is stopped mid-transfer (cancellation, lease loss and shutdown share one stop event), never blocks: the container is killed, the pipe closed and the writer joined. Oversized input is refused before start. Four tests, two with real containers |
| Trust boundary | The Gitleaks policy is explicitly `Workload.TRUSTED_TOOL`. `UNTRUSTED_CODE` cannot be combined with runc. The executor logs `scanner.runc_boundary` at startup under runc. Remote fetching and repository code execution remain absent |
| Exposure surfaces for paths | Paths reach only `findings.json` (safe form). Evidence is not exposed by any API endpoint. Audit records (`execution_events`) and metrics carry no paths; integration and E2E tests search evidence, results and audit rows for the synthetic values |

## Remaining risks (accepted, documented)

| Risk | Severity | Notes |
|---|---|---|
| runc shares the host kernel; a Gitleaks parser exploit gives code execution inside the sandbox | High for hostile content | ADR-0009 trust policy: acceptable only for synthetic or trusted content. Remote or hostile repositories require gVisor, Kata or a VM per job |
| Line-based allowlists of `generic-api-key` and `kubernetes-secret-yaml` | Medium | Content on the same line (for example `--mount=type=secret,`) suppresses these two generic rules. Removing them would make generic detection unusable. Provider-specific rules are unaffected |
| Name redaction is best-effort | Low | A secret in a name that matches no rule and is not high-entropy is persisted in its path. The heuristic also over-redacts harmless high-entropy names |
| Digests over raw material (`content_sha256`, `raw_report_sha256`) | Low | They cannot be inverted, but can confirm a complete guess of the input. They must not be published outside the tenant without review (M5) |
| A compromised sandbox can misreport its own job | Medium | Integrity, not authenticity (ADR-0008); attestation is M6 |
| The pre-extraction check depends on BusyBox `tar -tv` output | Low | The image is digest-pinned; the real-container tests fail if the format changes |
| Worker memory per job | Low | Snapshot plus archive plus stdout buffer, up to about 50 MiB |
