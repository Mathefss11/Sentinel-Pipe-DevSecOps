# Runbook: Gitleaks scanner

Design: [ADR-0010](../adr/0010-scanner-adapters-repository-snapshots-and-findings.md).
Threat model: [Gitleaks scanner](../threat-model/gitleaks-scanner.md). General execution
operations: [execution runbook](execution.md).

**Scope in this version:** development and CI only. Gitleaks scans synthetic repositories
from a local fixture directory. The worker refuses it in `production`, and the API
refuses `GITLEAKS` in `planned-scanners` under production profiles.

## 1. Pinned image

| | |
|---|---|
| Version | Gitleaks **8.30.1** (released 2026-03-21, revision `83d9cd68`) |
| Image | `ghcr.io/gitleaks/gitleaks@sha256:c00b6bd0aeb3071cbcb79009cb16a60dd9e0a7c60e2be9ab65d25e6bc8abbb7f` |
| Digest type | Multi-platform OCI index (linux/amd64, linux/arm64); the identical digest is published as `docker.io/zricethezav/gitleaks:v8.30.1` |
| Userland | Alpine with BusyBox (`/bin/sh`, `tar`, `base64`, `find`, `wc`) |
| Defined in | `GITLEAKS_IMAGE`, `sentinel_worker/sandbox/policy.py`; CI pre-pulls the same digest |
| Ruleset | `sentinel_worker/scanners/gitleaks-rules.toml`: the upstream v8.30.1 default configuration (SHA-256 `e163e53b…a329caf`) **without path-based allowlists**, generated by `scripts/dev/derive-gitleaks-rules.py`. Never edit it by hand |

Provision it on every worker host before starting workers (workers never pull):

```powershell
docker pull ghcr.io/gitleaks/gitleaks@sha256:c00b6bd0aeb3071cbcb79009cb16a60dd9e0a7c60e2be9ab65d25e6bc8abbb7f
.\.venv\Scripts\sentinel-worker.exe sandbox-check --profile gitleaks
```

`sandbox-check --profile gitleaks` must report `healthy` (13/13 controls) on that host.

## 2. Running a Gitleaks worker locally

1. Create a fixture directory with synthetic repositories at `<root>/<owner>/<name>`.
   The owner and name are the project's repository owner and name. Use only synthetic
   credentials, and generate them at test time rather than committing them.
2. Configure the API to plan Gitleaks jobs (`local` profile):
   `SENTINEL_EXECUTION_PLANNED_SCANNERS=GITLEAKS`.
3. Start the worker:

```powershell
$env:SENTINEL_WORKER_GITLEAKS_ENABLED = "true"
$env:SENTINEL_WORKER_REPOSITORY_FIXTURES_DIR = "C:\sentinel-fixtures"
.\.venv\Scripts\sentinel-worker.exe execute --idle-timeout 60
```

| Variable | Default | Meaning |
|---|---|---|
| `SENTINEL_WORKER_GITLEAKS_ENABLED` | `false` | Execute `GITLEAKS` jobs (refused in `production`) |
| `SENTINEL_WORKER_REPOSITORY_FIXTURES_DIR` | none | Absolute path of an existing directory (not a link) holding `<owner>/<name>` fixtures |
| `SENTINEL_WORKER_SANDBOX_TIMEOUT_SECONDS`, `_CPUS`, `_RUNTIME` | 300, 1, runc | Shared with the FIXTURE sandbox |

The memory (512 MiB), PID (128), tmpfs (96 MiB), stdin (32 MiB) and stdout (2 MiB)
limits of the Gitleaks policy are fixed in code. `SENTINEL_WORKER_FIXTURE_ENABLED` and
`SENTINEL_WORKER_GITLEAKS_ENABLED` can be combined; one worker then serves both scanner
types.

## 3. Reading results

Each completed job stores one evidence artifact, `findings.json` (`findings.v1`,
[contract](../api/findings-contract-v1.md)). Key fields:

- `execution.status`: `FINDINGS_DETECTED` (script exit 41, 42 or 43: leaks in content,
  in file names, or both) or `NO_FINDINGS` (exit 0).
- `coverage.complete` and `coverage.limitations`: what the scan could not see.
- `input.skipped`: per-reason counts of entries left out of the snapshot.
- `findings[]`: rule, location and fingerprint. There is **never** an excerpt of the
  secret. Severity, confidence and remediation are `null` because Gitleaks does not
  provide them.
- `location.target = FILE_PATH`: the secret is in the file's **name**. Paths are stored
  only in a safe form: components that were detected or look like credentials appear as
  `[redacted-N]` (`location.path_redacted`, `input.paths_redacted`). To locate the file,
  look in the repository itself; the raw name is not stored anywhere.

The scan's security decision stays `INCOMPLETE` (`POLICY_EVALUATION_UNAVAILABLE`) until
policy evaluation exists (M4), with or without findings.

## 4. Failures

Worker logs carry `scanner.input_rejected`, `scanner.failed` (with a sanitized `code`) or
`scanner.completed` events. They never contain report content, paths of the host or
secret values.

| Log code | Job result | Meaning and action |
|---|---|---|
| `REPOSITORY_NOT_FOUND` | `SCANNER_ERROR` (retried) | No `<root>/<owner>/<name>` directory. Check the fixture layout and the project's repository |
| `REPOSITORY_INVALID` | `SCANNER_ERROR` | The owner or name is not a valid name, or a path component is a link. Never "fix" this with links |
| `INPUT_TOO_LARGE` | `RESOURCE_LIMIT_EXCEEDED` (final) | More than 5000 files or 16 MiB, or an archive over 32 MiB. Reduce the fixture |
| `INPUT_CHANGED`, `INPUT_UNREADABLE` | `SCANNER_ERROR` | The fixture changed or could not be read during the snapshot |
| `GITLEAKS_FAILED` (script exit 70) | `SCANNER_ERROR` | Gitleaks returned an error. Run `sandbox-check --profile gitleaks`; inspect the image |
| `INPUT_EXTRACTION_FAILED` / `INPUT_VERIFICATION_FAILED` (71/72) | `SCANNER_ERROR` | The sandbox did not receive exactly the snapshot (count or `sha256sum` digest mismatch). Never treated as clean |
| `INPUT_REJECTED` (75) | `SCANNER_ERROR` | The archive contained an entry other than a plain file or directory, an unsafe or duplicate name. The worker never builds such archives: **treat as an incident** |
| `REPORT_MISSING` (73) | `SCANNER_ERROR` | |
| `REPORT_TOO_LARGE` (74), `FINDINGS_LIMIT_EXCEEDED` | `RESOURCE_LIMIT_EXCEEDED` | Content report over 1 MiB, path report over 256 KiB, over 5000 raw entries or over 1000 distinct findings. Nothing is dropped silently |
| `UNREDACTED_REPORT` | `SCANNER_ERROR` | Gitleaks returned a non-redacted value. **Treat as an incident:** the image or flags are not what was reviewed |
| `INVALID_OUTPUT`, `INVALID_REPORT`, `UNKNOWN_PATH`, `INCONSISTENT_EXIT_CODE`, `INVALID_FINDING`, `UNEXPECTED_EXIT_CODE` | `SCANNER_ERROR` | The output does not match the reviewed format. Repeated occurrences indicate a changed or compromised image |

Timeouts, OOM, PID or output limits, cancellation and runtime failures behave as for every
sandbox (execution runbook §5).

## 5. Upgrading Gitleaks

A version change is a security change. Before updating `GITLEAKS_IMAGE`:

1. Read the release notes for new configuration sources, suppression mechanisms or
   report fields.
2. Resolve the new tag's index digest on both ghcr.io and docker.io
   (`docker buildx imagetools inspect`) and confirm that they match.
3. Regenerate the ruleset from the new upstream `config/gitleaks.toml`:
   - update `UPSTREAM_VERSION` and `UPSTREAM_SHA256` in
     `scripts/dev/derive-gitleaks-rules.py` after reviewing the upstream diff;
   - run the script; it refuses any other input;
   - review new allowlists. Any new **path-based** or line-based mechanism must be
     assessed as repository-controlled suppression.
4. Re-verify the behaviors ADR-0010 depends on:
   - the `--config` precedence over a target `.gitleaks.toml`;
   - the loading of `.gitleaksignore`;
   - `--ignore-gitleaks-allow`;
   - exit codes (0, `--exit-code`, 1 on errors) and empty-target behavior;
   - `--redact=100` output;
   - byte-column reporting on the path manifest;
   - the exact JSON report keys. The parser refuses unknown keys, so a new field fails
     closed until it is reviewed.
5. Update the digest in `policy.py`, `ci.yml`, this runbook, `IDENTITY.version`, and the
   version in the tests.
6. Run `sandbox-check --profile gitleaks`, `pytest -m sandbox` with
   `SENTINEL_REQUIRE_SANDBOX=1`, and the E2E profile.

## 6. Limitations

- Only the working tree of the snapshot is scanned: no Git history and no archives.
- The upstream default rules only (no custom rules). Path allowlists were removed, so no
  file name hides a file from the scan. The line-based allowlists of `generic-api-key`
  and `kubernetes-secret-yaml` remain: content on the same line (for example
  `--mount=type=secret,`) can suppress those two generic rules.
- Snapshots skip links, hard links, special files, oversized files and unsupported names.
  Each skip is counted, and coverage is then `complete: false`.
- The input is a local fixture, not the commit (`commit_verified: false`).
- Secrets in file names are detected with the same rules and redacted, with a heuristic
  as defense in depth. A secret that matches no rule and does not look high-entropy would
  be persisted in its path.
- `input.content_sha256` and `execution.raw_report_sha256` are digests over material that
  may contain secrets. They cannot be inverted but can confirm a complete guess, so do
  not publish them outside the tenant.
- Gitleaks under runc is acceptable for synthetic content only. Remote or hostile content
  requires the controls listed in the threat model's "Required before remote repository
  scanning".
